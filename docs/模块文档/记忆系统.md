## 1. 系统概览

Soul-Agent 的记忆系统模仿人类记忆的双存储模型，将信息分为**短期记忆**和**长期记忆**两个层次。短期记忆负责维持当前对话的上下文窗口；长期记忆则通过 SQLite 数据库与可选的向量数据库（ChromaDB）实现跨会话的知识持久化。

整个记忆系统由以下六个源文件组成：

```
memory/
├── __init__.py          # 模块导出
├── manager.py           # 记忆管理器（核心协调层）
├── short_term.py        # 短期记忆
├── long_term.py         # 长期记忆（SQLite 持久化）
├── retriever.py         # 记忆检索器（向量 + 关键词混合检索）
└── summarizer.py        # 对话摘要器
```

## 3. 短期记忆 (ShortTermMemory)

**文件：** `memory/short_term.py`

短期记忆是一个基于 Python `dataclass` 的轻量级内存结构，用于维护当前对话的消息滑动窗口。

### 数据结构

```python
@dataclass
class ShortTermMemory:
    messages: list       # 消息列表，每个元素为 {"role": str, "content": str}
    max_messages: int = 50  # 最大消息容量
```

### 核心方法

#### `add(role, content)`

向消息列表追加一条新消息。当消息数量超过 `max_messages` 时，执行裁剪逻辑：

```
裁剪策略：保留 messages[:1] + messages[-(max-1):]
```

这意味着**始终保留第一条消息**（通常是系统提示或对话开头），然后取最近的 `max_messages - 1` 条消息。

```
示例（max_messages = 5）：

添加第 6 条消息前：
  [msg0, msg1, msg2, msg3, msg4]

添加第 6 条消息后（先 append 再裁剪）：
  [msg0, msg1, msg2, msg3, msg4, msg5]
       ↓ 裁剪
  [msg0, msg2, msg3, msg4, msg5]
  ├──┘   └────────┬────────────┘
  首条保留     最近 4 条 (max-1)
```

#### `get_messages()`

返回消息列表的**副本**（浅拷贝），防止外部代码意外修改内部状态。

#### `clear()`

清空所有消息。

### 设计意图

| 特性 | 说明 |
|------|------|
| 固定窗口 | 50 条消息上限，控制 LLM 上下文长度和 token 开销 |
| 首条保留 | 确保系统级指令或对话背景不被丢弃 |
| 纯内存 | 无持久化，会话结束即清空 |

## 4. 长期记忆 (LongTermMemory)

**文件：** `memory/long_term.py`

长期记忆通过 `aiosqlite`（异步 SQLite）实现持久化存储，是整个记忆系统的数据基座。

### MemoryEntry 数据类

```python
@dataclass
class MemoryEntry:
    id: str                  # UUID 字符串
    content: str             # 记忆内容
    memory_type: str         # 记忆类型：fact / preference / event / summary
    importance: float        # 重要度，范围 [0, 1]
    created_at: datetime     # 创建时间
    last_accessed: datetime  # 最后访问时间
    access_count: int        # 访问计数
    metadata: dict           # 扩展元数据（JSON 序列化存储）
    similarity: float        # 检索时设置的相似度分数（非持久化字段）
```

#### 记忆类型说明

| 类型 | 含义 | 示例 |
|------|------|------|
| `fact` | 客观事实 | "用户是一名 Python 后端开发者" |
| `preference` | 用户偏好 | "用户喜欢简洁的代码风格" |
| `event` | 事件记录 | "用户今天参加了技术面试" |
| `summary` | 对话摘要 | "讨论了微服务架构的优缺点" |

### 核心方法

#### `initialize()`

创建数据库文件（自动创建父目录），并建立三张表和三个索引：

```sql
-- 记忆表
CREATE TABLE IF NOT EXISTS memories (
    id                    TEXT PRIMARY KEY,
    content               TEXT NOT NULL,
    memory_type           TEXT NOT NULL,
    importance            REAL NOT NULL,
    embedding_id          TEXT,
    source_conversation_id TEXT,
    created_at            TEXT NOT NULL,
    last_accessed         TEXT NOT NULL,
    access_count          INTEGER DEFAULT 0,
    metadata              TEXT DEFAULT '{}'
);

-- 对话表
CREATE TABLE IF NOT EXISTS conversations (
    id         TEXT PRIMARY KEY,
    title      TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

-- 消息表
CREATE TABLE IF NOT EXISTS messages (
    id              TEXT PRIMARY KEY,
    conversation_id TEXT NOT NULL,
    role            TEXT NOT NULL,
    content         TEXT,
    tool_calls      TEXT,
    created_at      TEXT NOT NULL,
    FOREIGN KEY (conversation_id) REFERENCES conversations(id)
);

-- 索引
CREATE INDEX IF NOT EXISTS idx_memories_type       ON memories(memory_type);
CREATE INDEX IF NOT EXISTS idx_memories_importance  ON memories(importance);
CREATE INDEX IF NOT EXISTS idx_messages_conversation ON messages(conversation_id);
```

#### `store(content, memory_type, importance, metadata)`

```
生成 UUID → INSERT INTO memories → 返回 memory_id
时间戳使用 datetime.now().isoformat()
```

#### `get_all(memory_type=None)`

```sql
-- memory_type 为 None 时
SELECT * FROM memories ORDER BY importance DESC

-- memory_type 有值时
SELECT * FROM memories WHERE memory_type = ? ORDER BY importance DESC
```

#### `search_by_keyword(keyword, top_k=10)`

```sql
SELECT * FROM memories
WHERE content LIKE '%keyword%'
ORDER BY importance DESC
LIMIT top_k
```

使用 SQL `LIKE` 进行模糊匹配，这是向量检索不可用时的回退方案。

#### `update_access(memory_id)`

```sql
UPDATE memories
SET last_accessed = ?, access_count = access_count + 1
WHERE id = ?
```

每次记忆被检索返回时调用，用于衰减计算和使用频率统计。

#### `delete(memory_id)`

```sql
DELETE FROM memories WHERE id = ?
```

#### `_row_to_entry(row)`

将 `aiosqlite.Row` 对象转换为 `MemoryEntry` 数据类实例，其中 `metadata` 字段从 JSON 字符串反序列化为 Python 字典。

## 5. 记忆检索器 (MemoryRetriever)

**文件：** `memory/retriever.py`

记忆检索器是整个系统中逻辑最复杂的组件，实现了**向量语义检索 + 关键词匹配**的混合检索策略，并通过多因子综合评分对结果排序。

### ChromaDB 可选集成

```python
try:
    import chromadb
    CHROMADB_AVAILABLE = True
except ImportError:
    CHROMADB_AVAILABLE = False
```

检索器在运行时检测 ChromaDB 是否可用。即使 ChromaDB 不存在，系统也能通过关键词检索正常工作（优雅降级）。

### 初始化逻辑

```
__init__(long_term, vector_db_path=None)
    │
    ├── ChromaDB 可用 且 vector_db_path 有值？
    │     ├── 是 → PersistentClient(path=vector_db_path)   # 持久化向量库
    │     └── 否 → chromadb.Client()                       # 内存临时向量库
    │
    ├── 创建/获取 collection "soul_memories"
    │     └── metadata: {"hnsw:space": "cosine"}           # 余弦距离空间
    │
    └── 任何异常 → _collection = None（优雅降级）
```

### `has_vector_search` 属性

```python
@property
def has_vector_search(self) -> bool:
    return self._collection is not None
```

### 检索流程 (`retrieve`)

```
retrieve(query, top_k=5)
    │
    ├── 1. 获取候选集：_get_candidates(query, top_k * 3)
    │         │
    │         ├── 优先：_vector_search(query, top_k*3)
    │         │
    │         └── 回退：_keyword_search(query, top_k*3)
    │
    ├── 2. 对每条候选计算综合分数：
    │         final_score = similarity × 0.5
    │                     + importance × 0.3
    │                     + recency    × 0.2
    │
    ├── 3. 按 final_score 降序排列，取前 top_k 条
    │
    └── 4. 对返回的每条记忆调用 update_access()
```

#### 为什么先取 `top_k * 3` 再裁剪到 `top_k`？

候选集扩大 3 倍是为了给综合评分留出重新排序的空间。向量相似度最高的结果不一定是最终最优解——一条相似度稍低但重要度极高、最近被频繁访问的记忆，综合分数可能反超。

### 向量检索 (`_vector_search`)

```
_vector_search(query, top_k)
    │
    ├── collection.query(query_texts=[query], n_results=top_k)
    │     │
    │     └── ChromaDB 自动对 query 进行嵌入编码
    │
    ├── 距离转相似度：similarity = max(0, 1 - distance)
    │     │
    │     └── ChromaDB 余弦空间返回的 distance ∈ [0, 2]
    │         similarity ∈ [0, 1]（distance > 1 时截断为 0）
    │
    └── 从 long_term.get_all() 查找完整 MemoryEntry
          │
          └── 将 similarity 赋值到 entry.similarity 字段
```

**距离-相似度转换示意：**

```
distance:    0.0    0.2    0.5    0.8    1.0    1.5    2.0
             │      │      │      │      │      │      │
similarity:  1.0    0.8    0.5    0.2    0.0    0.0    0.0
```

### 关键词检索 (`_keyword_search`)

当向量检索不可用或失败时启用。

```
_keyword_search(query, top_k)
    │
    ├── 将 query 按空格分词
    │     例："Python 后端开发" → ["Python", "后端开发"]
    │
    ├── 对每个关键词调用 long_term.search_by_keyword()
    │     │
    │     └── SQL LIKE '%keyword%' 模糊匹配
    │
    ├── 按 id 去重合并结果
    │     │
    │     └── 所有匹配记忆的 similarity 设为 0.5（固定值）
    │
    └── 若无任何匹配：
          │
          └── 返回按重要度排序的记忆，similarity 设为 0.3
              （兜底策略：即使无关键词命中也能返回有价值的记忆）
```

### 时间衰减模型 (`_recency_score`)

采用指数衰减函数，半衰期为 **72 小时（3 天）**。

```
decay_rate = ln(2) / 72 ≈ 0.00963

recency_score = e^(-decay_rate × hours_ago)
```

#### 衰减曲线

```
分数
1.0 ┤ ●
    │  ╲
0.9 ┤   ╲
    │    ╲
0.8 ┤     ╲
    │      ╲
0.7 ┤       ╲
    │        ╲
0.6 ┤         ╲
    │          ╲
0.5 ┤───────────●─ 半衰期 (72h)
    │             ╲
0.4 ┤              ╲
    │               ╲
0.3 ┤                ╲
    │                 ╲
0.2 ┤──────────────────●─ 7天 (168h)
    │                    ╲
0.1 ┤                     ╲──────
    │                            ╲──────────
0.0 ┼───┬───┬───┬───┬───┬───┬───┬───┬───┬───
    0  24  48  72  96  120 144 168    360  720
                    小时                (30天)
```

#### 关键时间点对照表

| 时间距今 | hours_ago | recency_score | 含义 |
|----------|-----------|---------------|------|
| 刚刚 | 0 | **1.000** | 完全新鲜 |
| 1 小时 | 1 | **0.990** | 几乎无衰减 |
| 12 小时 | 12 | **0.891** | 轻微衰减 |
| 1 天 | 24 | **0.794** | 仍然较新鲜 |
| 3 天 | 72 | **0.500** | 半衰期，50% 分数 |
| 7 天 | 168 | **0.198** | 明显衰减 |
| 14 天 | 336 | **0.039** | 几乎遗忘 |
| 30 天 | 720 | **0.001** | 基本为零 |

## 6. 对话摘要器 (ConversationSummarizer)

**文件：** `memory/summarizer.py`

### 摘要提示词

```
请对以下对话内容生成一个简洁的摘要...控制在200字以内
```

### 双模式运行

```
summarize(messages)
    │
    ├── LLM 可用？
    │     ├── 是 → 发送 SUMMARIZE_PROMPT + 格式化消息 → LLM 生成摘要
    │     └── 否 → _simple_summary(messages)
    │
    └── 返回摘要字符串
```

### 消息格式化 (`_format_messages`)

```
输入：[{"role": "system", "content": "..."}, {"role": "user", "content": "你好"},
       {"role": "assistant", "content": "你好！有什么可以帮助你的？"}]

输出（跳过 system 角色）：
"用户: 你好\n助手: 你好！有什么可以帮助你的？"
```

### 简单摘要回退 (`_simple_summary`)

当 LLM 不可用时的降级方案：

```
1. 过滤出 role == "user" 的消息
2. 取前 5 条
3. 每条内容截断到 50 字符
4. 拼接为："对话主题: msg1; msg2; msg3; ..."
```

## 7. 记忆管理器 (MemoryManager)

**文件：** `memory/manager.py`

MemoryManager 是整个记忆系统的门面（Facade），协调所有子组件并对外提供统一接口。

### 构造函数

```python
def __init__(self, config: MemoryConfig, llm_client=None):
    self.short_term  = ShortTermMemory()
    self.long_term   = LongTermMemory(config.db_path)
    self.retriever   = MemoryRetriever(self.long_term, config.vector_db_path)
    self.summarizer  = ConversationSummarizer(llm_client)
```

### process_turn —— 核心写入流程

这是记忆系统最关键的方法，在每轮对话结束后被调用。

```
process_turn(user_input, assistant_reply)
    │
    ├── 1. 短期记忆：无条件写入
    │      short_term.add("user", user_input)
    │      short_term.add("assistant", assistant_reply)
    │
    ├── 2. 检查：LLM 是否可用 且 记忆提取是否启用？
    │      ├── 否 → 返回（仅保留短期记忆）
    │      └── 是 → 继续
    │
    ├── 3. 发送 EXTRACT_MEMORIES_PROMPT 给 LLM
    │      │
    │      │  prompt 内容：
    │      │  ┌──────────────────────────────────────────────┐
    │      │  │ 分析以下对话，提取需要长期记住的信息。          │
    │      │  │ 每条记忆用JSON格式输出，包含 content,          │
    │      │  │ memory_type(fact/preference/event),           │
    │      │  │ importance(0-1)。                             │
    │      │  │ 如果没有需要记住的信息，返回空数组 []。         │
    │      │  │                                              │
    │      │  │ 用户: {user_input}                           │
    │      │  │ 助手: {assistant_reply}                      │
    │      │  │                                              │
    │      │  │ 输出格式（纯JSON数组，不要markdown）:           │
    │      │  │ [{"content":"...","memory_type":"fact",       │
    │      │  │   "importance":0.7}]                         │
    │      │  └──────────────────────────────────────────────┘
    │      │
    │      ▼
    │
    ├── 4. 解析 LLM 返回的 JSON
    │      │
    │      ├── 处理 markdown 代码围栏
    │      │     例：```json\n[...]\n``` → [...]
    │      │
    │      └── json.loads() 解析为列表
    │
    ├── 5. 过滤：importance >= importance_threshold (0.3)
    │
    ├── 6. 对每条通过过滤的记忆调用 self.store()
    │
    └── 7. 异常处理：
           ├── JSONDecodeError  → 捕获，继续运行
           ├── KeyError         → 捕获，继续运行
           └── Exception        → 捕获，继续运行
```

### store —— 双写存储

```
store(content, memory_type, importance, metadata)
    │
    ├── long_term.store(...)        # 写入 SQLite
    │     └── 返回 memory_id
    │
    └── retriever.add_embedding(memory_id, content, metadata)
          └── ChromaDB collection.upsert(...)  # 写入向量库
```

### forget —— 双删除

```
forget(memory_id)
    │
    ├── long_term.delete(memory_id)         # 从 SQLite 删除
    └── retriever.delete_embedding(memory_id)  # 从 ChromaDB 删除
```

### retrieve —— 检索委托

```
retrieve(query, top_k=5)
    │
    └── retriever.retrieve(query, min(top_k, max_memories_per_query))
```

`max_memories_per_query` 来自 MemoryConfig，用于限制单次查询返回的最大记忆条数。

### list_all —— 列出所有记忆

```
list_all(memory_type=None)
    │
    └── long_term.get_all(memory_type)
```

### summarize_conversation —— 生成摘要

```
summarize_conversation()
    │
    ├── messages = short_term.get_messages()
    └── summarizer.summarize(messages)
```

## 10. 评分公式与衰减模型

### 综合评分公式

每条候选记忆的最终排序分数由三个因子加权求和：

```
final_score = similarity  × 0.5      ← 语义/关键词相关性
            + importance  × 0.3      ← 记忆固有重要度
            + recency     × 0.2      ← 时间新鲜度
```

#### 各因子分析

| 因子 | 权重 | 来源 | 值域 |
|------|------|------|------|
| `similarity` | 0.5 | 向量距离转换 或 关键词匹配固定值 | [0, 1] |
| `importance` | 0.3 | 记忆创建时由 LLM 赋值 | [0, 1] |
| `recency` | 0.2 | 指数衰减函数计算 | (0, 1] |

#### final_score 理论范围

```
最小值：0 × 0.5 + 0 × 0.3 + 0 × 0.2 = 0.0
最大值：1 × 0.5 + 1 × 0.3 + 1 × 0.2 = 1.0
```

### 评分计算完整示例

假设有三条候选记忆，当前时间为 2026-06-01 12:00：

```
记忆 A: "用户是Python开发者"
  similarity = 0.85 (向量匹配)
  importance = 0.9
  last_accessed = 2026-06-01 10:00 (2小时前)
  recency = e^(-0.00963 × 2) = 0.981

  final_score = 0.85×0.5 + 0.9×0.3 + 0.981×0.2
              = 0.425 + 0.270 + 0.196
              = 0.891

记忆 B: "用户喜欢TypeScript"
  similarity = 0.70
  importance = 0.6
  last_accessed = 2026-05-28 12:00 (96小时前 / 4天前)
  recency = e^(-0.00963 × 96) = 0.397

  final_score = 0.70×0.5 + 0.6×0.3 + 0.397×0.2
              = 0.350 + 0.180 + 0.079
              = 0.609

记忆 C: "用户今天讨论了数据库优化"
  similarity = 0.60
  importance = 0.5
  last_accessed = 2026-06-01 11:30 (0.5小时前)
  recency = e^(-0.00963 × 0.5) = 0.995

  final_score = 0.60×0.5 + 0.5×0.3 + 0.995×0.2
              = 0.300 + 0.150 + 0.199
              = 0.649
```

**排序结果：A (0.891) > C (0.649) > B (0.609)**

注意：记忆 C 虽然语义相似度和重要度都低于 B，但因为极高的新鲜度，综合分数反超。

## 11. 实际场景分析

### 场景一：日常对话——提取有价值的记忆

```
用户: "我叫李明，在北京做前端开发，最近在学 Rust。"
助手: "你好李明！前端转 Rust 是个不错的选择..."
```

**LLM 提取结果：**

```json
[
  {"content": "用户名叫李明", "memory_type": "fact", "importance": 0.8},
  {"content": "用户在北京工作", "memory_type": "fact", "importance": 0.6},
  {"content": "用户是前端开发者", "memory_type": "fact", "importance": 0.8},
  {"content": "用户正在学习Rust", "memory_type": "event", "importance": 0.7}
]
```

**过滤（阈值 0.3）：** 全部通过 ✓

**写入路径：** 4 条记忆 → SQLite + ChromaDB 双写

### 场景二：闲聊——无需记忆

```
用户: "今天天气不错"
助手: "是啊，阳光明媚的日子总让人心情愉悦。"
```

**LLM 提取结果：**

```json
[]
```

空数组，不触发任何存储操作。短期记忆正常记录这轮对话。

### 场景三：重要度过滤

```
用户: "帮我看看这段代码，我之前好像用的是 VS Code"
助手: "好的，让我分析一下这段代码..."
```

**LLM 提取结果：**

```json
[
  {"content": "用户可能使用VS Code编辑器", "memory_type": "preference", "importance": 0.2}
]
```

**过滤（阈值 0.3）：** importance 0.2 < 0.3，**被过滤** ✗

"可能使用"这种不确定信息被 LLM 赋予了较低的重要度，系统自动将其过滤。

### 场景四：检索与上下文注入

用户下一次提问：

```
用户: "帮我写一个 Rust 的 HTTP 服务器"
```

**检索过程：**

```
1. query = "帮我写一个Rust的HTTP服务器"

2. 向量检索返回候选集（top_k*3 = 15 条）：
   - "用户正在学习Rust"        → similarity = 0.82
   - "用户是前端开发者"         → similarity = 0.41
   - "用户名叫李明"            → similarity = 0.15
   ...

3. 综合评分（假设都是刚存入的，recency ≈ 0.99）：

   "用户正在学习Rust":
     0.82×0.5 + 0.7×0.3 + 0.99×0.2 = 0.410 + 0.210 + 0.198 = 0.818

   "用户是前端开发者":
     0.41×0.5 + 0.8×0.3 + 0.99×0.2 = 0.205 + 0.240 + 0.198 = 0.643

   "用户名叫李明":
     0.15×0.5 + 0.8×0.3 + 0.99×0.2 = 0.075 + 0.240 + 0.198 = 0.513

4. 排序取 top_k=5：返回上述记忆
```

**系统提示词注入：**

```
已知的用户信息：
- [event] 用户正在学习Rust
- [fact] 用户是前端开发者
- [fact] 用户名叫李明
- [fact] 用户在北京工作
```

LLM 在回答时就能根据这些上下文给出更个性化的回复，比如考虑到用户的前端背景来类比解释 Rust 概念。

### 场景五：LLM 不可用时的降级

```
ChromaDB 未安装，LLM 服务不可达

写入侧：
  → 短期记忆正常写入 ✓
  → 长期记忆提取跳过（LLM 不可用）✗

检索侧：
  → 向量检索不可用，回退到关键词检索
  → 关键词匹配的 similarity 固定为 0.5
  → 无匹配时返回最重要的记忆（similarity = 0.3）

摘要侧：
  → _simple_summary 回退
  → 取前 5 条用户消息，截断拼接
```

### 场景六：短期记忆溢出

假设 `max_messages = 5`，对话进行到第 6 轮：

```
初始状态（5条消息已满）：
  [system_prompt, user1, asst1, user2, asst2]

第3轮对话 → add("user", user3)：
  [system_prompt, user1, asst1, user2, asst2, user3]
  超出限制 → 裁剪：
  [system_prompt, asst1, user2, asst2, user3]
  │             └──────────┬──────────────┘
  首条保留          最近 4 条

继续 → add("assistant", asst3)：
  [system_prompt, asst1, user2, asst2, user3, asst3]
  超出限制 → 裁剪：
  [system_prompt, user2, asst2, user3, asst3]
```

系统提示词始终保留在首位，最早的对话轮次逐步被淘汰。
