# 核心模块

本文档描述 `soul_agent/core/` 模块的内部结构。核心模块负责 Agent 主循环、对话消息构建、上下文裁剪和任务规划，是 Soul-agent 的执行中枢。

---

## 1. 模块组成

```
soul_agent/core/
├── __init__.py
├── agent.py          # Agent 主循环，ReAct 执行引擎
├── conversation.py   # 对话历史与 LLM 消息构建
├── context.py        # 上下文窗口管理与 token 粗估
├── planner.py        # 任务规划器，LLM 驱动的步骤拆解
└── plan_tracker.py   # 计划进度追踪器，将工具调用匹配到计划步骤
```

| 文件 | 主要对象 | 职责 |
|------|----------|------|
| `agent.py` | `Agent` | 协调 LLM、记忆系统、工具系统，自动规划并执行完整用户请求 |
| `conversation.py` | `Conversation` | 构建系统提示词、注入记忆与计划上下文、维护多轮历史 |
| `context.py` | `ContextManager` | 粗略估算 token 数，裁剪过长消息 |
| `planner.py` | `TaskPlanner` | 将复杂任务拆解为结构化步骤（含复杂度评估） |
| `plan_tracker.py` | `PlanTracker`, `PlanStep` | 追踪计划执行进度，将工具调用匹配到计划步骤 |

## 2. Agent 主循环

`Agent` 是核心模块的入口类，位于 `agent.py`。

### 2.1 构造函数依赖

```python
class Agent:
    def __init__(self, config, llm_client, memory_manager, tool_registry, tool_executor):
        self.config = config
        self.llm = llm_client
        self.memory = memory_manager
        self.tools = tool_registry
        self.executor = tool_executor
        self.conversation = Conversation()
        self.context_mgr = ContextManager(max_tokens=config.llm.max_tokens)
        self.planner = TaskPlanner(llm_client)
        self._plan_tracker = None              # 计划进度追踪器
        self._on_tool_call = None              # UI 回调：工具调用
        self._on_tool_result = None            # UI 回调：工具执行结果
        self._on_plan_progress = None          # UI 回调：计划进度
```

Agent 不直接创建依赖，而是通过构造函数注入：

| 依赖 | 类型 | 作用 |
|------|------|------|
| `config` | `AppConfig` | 读取最大迭代次数、LLM token 配置、planning 开关等 |
| `llm_client` | `LLMClient` | 调用模型生成回复或工具调用 |
| `memory_manager` | `MemoryManager` | 检索相关记忆、处理新记忆 |
| `tool_registry` | `ToolRegistry` | 提供工具 schema 和工具描述 |
| `tool_executor` | `ToolExecutor` | 执行 LLM 返回的工具调用 |

这种设计使核心模块不依赖具体实现，便于测试时使用 mock 对象替换 LLM、记忆或工具。

### 2.2 单轮执行流程

`Agent.run(user_input)` 是处理一次用户输入的完整流程。

```
用户输入
  │
  ▼
确保会话已持久化
  │
  ▼
自动判断任务复杂度 → 若复杂则生成执行计划
  │
  ▼
检索相关记忆 memory.retrieve(user_input)
  │
  ▼
构建系统提示词 SYSTEM_PROMPT + 工具描述 + 计划上下文
  │
  ▼
Conversation.build_messages()
  │
  ▼
调用 LLM，附带工具 schema
  │
  ├─ 返回 tool_calls ─→ 通知 UI → 执行工具 → 通知 UI 结果 → 工具结果加入 messages → 持久化到 Conversation ─┐
  │                                                                                                    │
  └─ 返回普通文本 ─────────────────────────────────────────────────────────────────────────────────────┘
  │
  ▼
更新长期记忆 memory.process_turn()
  │
  ▼
添加助手回复到对话历史，裁剪过长消息
  │
  ▼
返回最终回复
```

### 2.3 ReAct 循环

Agent 使用 ReAct（Reasoning + Acting）模式：

```python
for i in range(max_iter):
    response = await self.llm.chat(
        messages,
        tools=self.tools.schemas if self.tools.schemas else None,
        stream=False,
    )

    if response.has_tool_calls:
        # 执行工具，把结果加入 messages，再回到 LLM
        ...
    else:
        final_content = response.content
        break
```

特点：

1. **模型自主决定是否调用工具**：Agent 只提供工具 schema，不预先固定执行路径。
2. **工具结果回传模型**：工具输出以 `role="tool"` 消息加入上下文，模型基于结果继续推理。
3. **最大轮数保护**：由 `config.agent.max_iterations` 控制，默认 30，耗尽时返回明确中断提示并引导用户输入"继续"恢复。
4. **最终文本退出**：当模型不再返回工具调用时，循环结束。
5. **工具消息持久化**：每次工具调用后，assistant（含 tool_calls）和 tool result 消息自动同步到 `Conversation`，确保用户输入"继续"时 LLM 不丢失上下文。
6. **空内容防御**：当 max_iterations 耗尽且 LLM 返回空内容（工具调用轮 content 为 null）时，返回有意义的提示信息而非空白。

### 2.4 工具调用消息格式

当 LLM 返回工具调用时，Agent 会构造 assistant 消息：

```python
assistant_msg = {
    "role": "assistant",
    "content": response.content or "",
    "tool_calls": [
        {
            "id": tc["id"],
            "type": "function",
            "function": {
                "name": tc["name"],
                "arguments": json.dumps(tc["arguments"], ensure_ascii=False),
            },
        }
    ],
}
```

随后调用：

```python
results = await self.executor.execute_batch(response.tool_calls)
messages.extend(results)
```

`ToolExecutor` 返回的结果消息形如：

```python
{
    "role": "tool",
    "tool_call_id": "call_xxx",
    "content": "工具输出内容"
}
```

这是 OpenAI function calling 对话格式的标准结构。

### 2.5 UI 回调机制

Agent 提供四个轻量回调：

```python
def set_callbacks(self, on_tool_call=None, on_stream=None, on_plan_progress=None, on_tool_result=None):
    self._on_tool_call = on_tool_call
    self._on_stream = on_stream
    self._on_plan_progress = on_plan_progress
    self._on_tool_result = on_tool_result
```

| 回调 | 触发时机 | 参数 |
|------|---------|------|
| `on_tool_call` | 工具调用开始前 | `(tool_name, arguments_dict)` |
| `on_tool_result` | 工具执行完成后 | `(tool_name, success_bool, output_str, error_str_or_None)` |
| `on_plan_progress` | 计划进度更新时 | `(plan_tracker_instance)` |
| `on_stream` | 流式输出时（预留） | `(chunk_str)` |

`on_tool_call` 触发时通知 UI 展示"正在调用什么工具"：

```python
if self._on_tool_call:
    for tc in response.tool_calls:
        self._on_tool_call(tc["name"], tc["arguments"])
```

`on_tool_result` 触发时通知 UI 工具执行结果（成功显示 ✅ + 输出摘要，失败显示 ❌ + 错误信息）。

`on_plan_progress` 触发时通知 UI 刷新计划面板（Live 刷新模式，显示各步骤完成状态）。

这样核心逻辑不直接依赖 Rich 或终端输出，保持 Core 与 UI 解耦。

## 3. Conversation 对话管理

`Conversation` 位于 `conversation.py`，负责维护当前对话历史和构建发给 LLM 的消息列表。

### 3.1 内部状态

```python
class Conversation:
    def __init__(self):
        self.messages: list[dict] = []
        self.conversation_id: str = str(uuid.uuid4())  # 自动生成
        self._on_persist_message = None  # fire-and-forget 持久化回调
```

`messages` 只保存历史用户/助手消息，不保存当前用户输入，也不保存系统提示词。
`conversation_id` 是一个 UUID，用于标识当前会话（持久化到数据库）。
`_on_persist_message` 由 Agent 通过 `set_persist_callback()` 注入，`add_turn()` 和 `add_message()` 自动调用。

### 3.2 消息构建

```python
def build_messages(self, user_input, system_prompt, memories=None, plan_context="") -> list[dict]:
```

输出结构：

```
[
  {"role": "system", "content": "系统提示词 + 记忆上下文 + 计划上下文 + 工具描述"},
  ...历史消息（含工具调用和工具结果消息）,
  {"role": "user", "content": 当前输入}
]
```

`plan_context` 参数用于在系统提示词中注入任务执行计划（由 `TaskPlanner` 生成，`Agent._format_plan_context()` 格式化）。

### 3.3 记忆注入格式

当 `memories` 非空时，会生成：

```text
已知的用户信息：
- [fact] 用户是计算机专业学生
- [preference] 用户喜欢简洁代码
```

然后填入系统提示词的 `{memory_context}` 占位符。`plan_context` 同时填入 `{plan_context}` 占位符。

这种设计有两个好处：

1. 记忆作为上下文信息，而不是系统指令，降低记忆投毒风险。
2. 每条记忆保留类型标签，模型能区分事实、偏好、事件等信息。

### 3.4 历史裁剪

```python
def add_turn(self, user_input, assistant_reply):
    self.messages.append({"role": "user", "content": user_input})
    self.messages.append({"role": "assistant", "content": assistant_reply})

    max_turns = 20
    max_messages = max_turns * 2
    if len(self.messages) > max_messages:
        self.messages = self.messages[-max_messages:]
```

当前保留最近 20 轮对话，即最多 40 条消息。旧消息会被丢弃，但重要信息可以通过长期记忆系统保留下来。

## 4. ContextManager 上下文管理

`ContextManager` 位于 `context.py`，用于控制消息总量不要超过模型上下文限制。

### 4.1 Token 粗估算法

```python
def estimate_tokens(self, text: str) -> int:
    chinese_chars = sum(1 for c in text if '一' <= c <= '鿿')
    other_chars = len(text) - chinese_chars
    return int(chinese_chars * 1.5 + other_chars / 4)
```

估算规则：

| 字符类型 | 估算方式 |
|----------|----------|
| 中文字符 | 约 1.5 token / 字 |
| 其他字符 | 约 4 字符 / token |

这不是精确 tokenizer，而是轻量级近似，用于避免上下文明显超限。

### 4.2 消息裁剪策略

`trim_messages(messages, max_tokens=None)` 的原则：

1. 始终保留 system 消息。
2. 始终保留最后一条 user 消息。
3. 中间历史消息从新到旧保留，直到 token 预算耗尽。

```
原始消息：
[system, user1, assistant1, user2, assistant2, ..., userN]

裁剪后：
[system, 最近若干历史消息..., userN]
```

该策略确保当前请求和系统约束不丢失，同时最大化保留最近上下文。

### 新增：对话持久化

`Conversation` 新增 `set_persist_callback(callback)` 方法。当回调被注入后，每次 `add_turn()` 和 `add_message()` 自动通过 fire-and-forget 模式将消息异步写入 SQLite。回调由 `Agent._ensure_conversation_persisted()` 在首轮对话时注入。

`reset()` 清空当前对话并生成新的 `conversation_id`，旧会话数据保留在数据库中，可通过 `/history` 命令查看。

`Agent.rename_conversation(title)` 可用于给当前会话命名。

## 5. TaskPlanner 任务规划器

`TaskPlanner` 位于 `planner.py`，通过 LLM 将复杂任务拆解为结构化步骤。

### 5.1 提示词结构

规划器要求模型输出 JSON（包含复杂度评估）：

```json
{
  "task": "任务描述",
  "complexity": "simple|complex",
  "steps": [
    {
      "id": 1,
      "description": "步骤描述",
      "tool": "工具名称或null",
      "depends_on": []
    }
  ]
}
```

- `complexity: "simple"` 表示任务单轮即可完成
- `complexity: "complex"` 表示任务需要多步或使用工具

### 5.2 自动触发机制

`Agent.run()` 步骤 0.5 使用纯启发式方法快速估算任务复杂度（零 LLM 开销）：

1. **长度因子**：>80 字 +3，>40 字 +2，>15 字 +1
2. **指标词密度**：检测「然后」「分析」「创建」「部署」等 28 个复杂度关键词，每个 +1（上限 5）
3. **多句/多段落**：含 `。` 或换行 +2，含 `；` 或 `，` +1

复杂度 >= 阈值（默认 2）时自动调用 `TaskPlanner.plan()` 生成执行计划并创建 `PlanTracker`。

### 5.2 解析容错

模型可能返回 Markdown 代码块，因此代码做了兼容：

```python
if "```json" in content:
    content = content.split("```json")[1].split("```")[0].strip()
elif "```" in content:
    content = content.split("```")[1].split("```")[0].strip()
return json.loads(content)
```

如果解析失败，降级为单步骤计划：

```python
{
    "task": task,
    "complexity": "simple",
    "steps": [{"id": 1, "description": task, "tool": None, "depends_on": []}],
}
```

`TaskPlanner` 已完整接入 Agent 主循环，在 `Agent.run()` 的步骤 0.5 中根据任务复杂度自动触发，生成的计划通过 `_format_plan_context()` 格式化后注入系统提示词，并通过 `PlanTracker` 追踪执行进度。

## 6. PlanTracker 计划追踪器

`PlanTracker` 位于 `plan_tracker.py`，负责将 LLM 生成的执行计划转化为可追踪的状态。

### 6.1 PlanStep 数据结构

```python
@dataclass
class PlanStep:
    id: int               # 步骤序号
    description: str       # 步骤描述
    tool: str | None       # 需要的工具名（无则为 None）
    depends_on: list[int]  # 依赖的前置步骤 ID
    status: str = "pending"  # "pending" | "done"
```

### 6.2 PlanTracker 核心方法

```python
class PlanTracker:
    def mark_tool_done(self, tool_name: str) -> int | None:
        """匹配第一个 pending 步骤标记为 done，返回 step id 或 None"""
```

当 Agent 在 ReAct 循环中执行完工具后，调用 `PlanTracker.mark_tool_done(tool_name)` 自动将计划中匹配的工具步骤标记为完成。UI 通过 `on_plan_progress` 回调接收 PlanTracker 实例，用 Rich Live 面板实时刷新进度显示。

**只读属性：**

| 属性 | 类型 | 说明 |
|------|------|------|
| `done_count` | `int` | 已完成步骤数 |
| `total_count` | `int` | 总步骤数 |
| `all_done` | `bool` | 全部步骤是否已完成 |
| `has_any_done` | `bool` | 是否有步骤已完成 |
| `has_tool_steps` | `bool` | 是否至少有一个需要工具的步骤 |

## 8. 设计特点

### 8.1 依赖注入

Agent 不直接创建 `LLMClient`、`MemoryManager` 或工具对象，而是由 `app.create_agent()` 创建后注入。这使得：

- 测试时可以用 mock 替换真实 LLM。
- 未来可以替换记忆系统实现。
- 工具系统可以动态配置。

### 8.2 Core/UI 解耦

Agent 不负责打印输出，只通过四个回调暴露事件：工具调用、工具结果、计划进度、流式输出。Rich 渲染逻辑全部在 `ui/` 模块。

### 8.3 ReAct + 自动规划

相比一次性规划执行，ReAct+规划更适合终端助手：

- 可根据工具输出动态调整下一步。
- 支持多轮观察与行动。
- 与 OpenAI function calling 格式天然契合。
- 零 LLM 开销的启发式复杂度评估自动触发规划，无需用户干预。

### 8.4 安全边界

Core 模块只调度工具，不直接执行文件系统、Shell、网络操作。具体安全限制由工具模块实现，例如命令黑名单、超时、输出截断等。
