## 1. 项目概览

Soul-Agent 是一个基于 Python 构建的终端 AI 助手。它采用 ReAct（Reasoning + Acting）循环架构，结合多级记忆系统和可扩展的工具体系，在终端环境中为用户提供智能对话与任务执行能力。

**核心技术栈：**

| 领域       | 技术选型                          |
| ---------- | --------------------------------- |
| CLI 框架   | Click                             |
| 终端 UI    | Rich + prompt_toolkit             |
| LLM 调用   | AsyncOpenAI（兼容 OpenAI 协议）   |
| 向量检索   | ChromaDB                          |
| 持久存储   | SQLite（aiosqlite 异步驱动）      |
| 配置管理   | Pydantic v2 + YAML                |
| 数据校验   | Pydantic v2 BaseModel             |

## 4. 各层详细设计

### 4.1 CLI 层

**文件：** `cli.py`、`app.py`

CLI 层是用户与系统交互的入口，基于 Click 框架提供四个子命令。

```
cli.py
├── chat   (默认命令) ── 进入交互式对话
├── ask    ── 单次提问，返回后退出
├── memory ── 记忆管理（查看/清理/导出）
└── config ── 配置查看与修改
```

**`app.py` — 组装胶水层：**

`app.py` 承担依赖注入与组件组装职责，核心函数 `create_agent()` 负责：

1. 调用 `load_config()` 加载配置
2. 根据配置实例化 `LLMClient`（选择 OpenAI 或 Local Provider）
3. 初始化 `MemoryManager`、`ToolRegistry`、`ToolExecutor`
4. 注册内置工具到 `ToolRegistry`
5. 组装 `Conversation`、`ContextManager`
6. 创建 `Agent` 实例并返回

这种设计将组件创建逻辑集中在一处，各模块本身无需关心依赖的来源。

### 4.2 UI 层

**目录：** `ui/`

| 组件           | 职责                                    | 技术依赖        |
| -------------- | --------------------------------------- | --------------- |
| `Renderer`     | Markdown 渲染、面板、表格、主题化输出   | Rich            |
| `InputHandler` | 用户输入处理、历史记录、自动建议        | prompt_toolkit  |
| `themes.py`    | 主题定义与切换                          | Rich Style      |

**主题系统：**

```
themes.py
├── default   ── 默认配色方案
├── monokai   ── Monokai 风格暗色主题
└── dracula   ── Dracula 风格暗色主题
```

`Renderer` 使用 Rich 库实现终端富文本渲染，支持 Markdown 语法高亮、代码块、面板边框和表格布局。`InputHandler` 基于 prompt_toolkit 实现多行编辑、输入历史（持久化到 `data/.input_history`）以及自动补全建议。

### 4.3 Core 核心层

**目录：** `core/`

核心层是系统的大脑，包含四个关键组件。

#### 4.3.1 Agent — ReAct 循环引擎

```
Agent.run(user_input)
│
├─► 确保会话已持久化
├─► 自动复杂度评估 → 若复杂则 TaskPlanner.plan() → PlanTracker
├─► 检索相关记忆 (MemoryManager.retrieve)
├─► 构建消息列表 (Conversation.build_messages + plan_context)
│
├─► ═══ ReAct 循环开始 ═══
│   │
│   ├─► 调用 LLM (带 tool schemas)
│   │
│   ├─► LLM 返回 tool_calls?
│   │   ├─ 是 → 通知 UI (on_tool_call)
│   │   │       ToolExecutor 执行工具
│   │   │       通知 UI 结果 (on_tool_result)
│   │   │       更新 PlanTracker 进度
│   │   │       工具消息持久化到 Conversation
│   │   │       回到循环顶部 ──────►
│   │   │
│   │   └─ 否 → 提取最终回复
│   │
│   └─► 迭代次数 ≥ max_iterations?
│       └─ 是 → 返回中断提示（含"继续"指引）
│
├─► ═══ ReAct 循环结束 ═══
│
├─► MemoryManager.process_turn() (异步记忆处理)
├─► 助手回复追加到 Conversation → 裁剪过长消息
│
└─► 返回最终回复
```

`Agent` 通过 `max_iterations` 参数（来自 `AgentConfig`，默认 30）控制最大工具调用轮次，防止无限循环。耗尽时返回有意义的提示信息，引导用户输入"继续"恢复执行。工具调用过程中的所有交互消息（assistant tool_calls + tool results）被持久化到 `Conversation`，确保"继续"时不丢失上下文。

#### 4.3.2 Conversation — 消息管理

`Conversation` 负责构建发送给 LLM 的完整消息列表，核心逻辑：

1. 构造 system prompt（注入记忆上下文 + 工具描述）
2. 拼接历史对话（最多保留 **20 轮**）
3. 追加当前用户输入
4. 交给 `ContextManager` 进行 token 裁剪

```
build_messages() 输出结构：
┌────────────────────────────────────┐
│ system:  SYSTEM_PROMPT             │
│          + {memory_context}        │
│          + {plan_context}          │
│          + {tool_descriptions}     │
├────────────────────────────────────┤
│ user:    历史消息 [1]              │
│ assistant: ...  (含 tool_calls)    │
│ tool:    工具结果                  │
│ ...                                │
│ user:    历史消息 [N] (N ≤ 20)    │
│ assistant: ...                     │
├────────────────────────────────────┤
│ user:    当前输入                   │
└────────────────────────────────────┘
```

#### 4.3.3 ContextManager — 上下文窗口管理

`ContextManager` 解决 LLM 上下文窗口有限的问题：

- **Token 估算**：针对中英文混合文本进行 token 数量估算（中文字符与英文单词采用不同比率）
- **消息裁剪**：当总 token 数超过模型限制时，从最旧的历史消息开始移除，始终保留 system prompt 和当前用户输入

#### 4.3.4 TaskPlanner — 任务规划

`TaskPlanner` 利用 LLM 将复杂用户请求分解为可执行的子任务序列，输出包含 `complexity`（simple/complex）评估的结构化计划。

**自动触发机制：** `Agent._estimate_complexity()` 使用纯启发式方法（零 LLM 开销）评估任务复杂度：长度因子 + 28 个复杂度指标词检测 + 多句判别。复杂度 >= 阈值（默认 2）时自动调用 `TaskPlanner.plan()`。

#### 4.3.5 PlanTracker — 计划进度追踪

`PlanTracker` 将 `TaskPlanner` 生成的计划转化为可追踪状态，包含 `PlanStep` 列表。当 Agent 在 ReAct 循环中执行工具时，自动将匹配的步骤标记为 done。UI 通过 Rich Live 组件在终端底部原位刷新进度面板（`📋 执行计划`），任务完成后自动收起。

### 4.4 Memory 记忆系统

**目录：** `memory/`

记忆系统是 Soul-Agent 的核心差异化能力，采用多级架构实现短期与长期记忆的协同。

#### 架构总览

```
┌──────────────────────────────────────────────────┐
│               MemoryManager (统一入口)             │
│                                                    │
│   retrieve()  ──  检索记忆                         │
│   process_turn()  ──  处理对话，提取/存储记忆       │
│   管理并编排以下所有子组件                          │
├───────────┬──────────────┬───────────────────────┤
│           │              │                        │
│  ┌────────▼────────┐  ┌─▼──────────────┐        │
│  │ ShortTermMemory │  │ LongTermMemory │        │
│  │ 会话级列表       │  │ SQLite 持久化   │        │
│  │ 最多 50 条      │  │ 3 张表          │        │
│  └─────────────────┘  └───────┬────────┘        │
│                               │                  │
│                     ┌─────────▼─────────┐        │
│                     │  MemoryRetriever  │        │
│                     │  混合检索引擎      │        │
│                     │  ChromaDB 向量     │        │
│                     │  + 关键词回退      │        │
│                     └───────────────────┘        │
│                                                    │
│  ┌──────────────────────────────────┐              │
│  │  ConversationSummarizer          │              │
│  │  LLM 摘要 / 简单回退             │              │
│  └──────────────────────────────────┘              │
└──────────────────────────────────────────────────┘
```

#### 4.4.1 ShortTermMemory — 短期记忆

- **存储方式**：Python 内存列表（会话级，进程退出即丢失）
- **容量限制**：最多 50 条，超出后按 FIFO 策略淘汰
- **用途**：保存当前会话内的关键交互片段，供本轮对话快速引用

#### 4.4.2 LongTermMemory — 长期记忆

基于 SQLite（通过 aiosqlite 异步驱动），包含三张表：

| 表名            | 用途                         |
| --------------- | ---------------------------- |
| `memories`      | 存储提取的记忆条目           |
| `conversations` | 存储对话摘要与元信息         |
| `messages`      | 存储完整对话消息历史         |

#### 4.4.3 MemoryRetriever — 混合检索引擎

`MemoryRetriever` 实现语义搜索与关键词搜索的混合检索策略。

**检索流程：**

```
用户查询
    │
    ├──► ChromaDB 向量相似度搜索
    │         │
    │         ▼
    │    相似度得分 (similarity)
    │
    ├──► 关键词匹配回退
    │    (当向量搜索结果不足时启用)
    │
    └──► 混合评分计算
              │
              ▼
         最终排序 → top-k 返回
```

**混合评分公式：**

```
score = similarity × 0.5 + importance × 0.3 + recency × 0.2
```

| 因子         | 权重 | 说明                                      |
| ------------ | ---- | ----------------------------------------- |
| similarity   | 0.5  | ChromaDB 返回的向量余弦相似度             |
| importance   | 0.3  | 记忆条目的重要性评级（存储时标记）        |
| recency      | 0.2  | 时间衰减分数，越近期分数越高              |

**时间衰减模型：**

采用指数衰减函数，半衰期为 **72 小时**：

```
recency = 0.5 ^ (elapsed_hours / 72)

示意：
1.0 ┤ *
    │  *
0.5 ┤    *  ← 72h 后衰减至 0.5
    │       *
0.25┤          *  ← 144h 后衰减至 0.25
    │              *
0.0 ┤─────────────────────►
    0   72  144  216  (小时)
```

这意味着 3 天前的记忆相关性权重降至一半，6 天前降至四分之一，确保近期记忆获得更高优先级，同时不完全遗忘旧记忆。

#### 4.4.4 ConversationSummarizer — 对话摘要

提供两种摘要策略：

- **LLM 摘要**（首选）：将对话历史发送给 LLM 生成结构化摘要
- **简单回退**：当 LLM 不可用时，基于规则截取关键信息作为摘要

### 4.5 Tools 工具系统

**目录：** `tools/`

工具系统采用注册 + 执行的解耦架构，支持 OpenAI function calling 协议。

#### 类层次结构

```
Tool (ABC 抽象基类)
│
│   定义接口：
│   ├── name: str
│   ├── description: str
│   ├── execute(**kwargs) -> str    [抽象方法]
│   └── to_schema() -> dict         [生成 OpenAI function schema]
│
├── ReadFileTool
├── WriteFileTool
├── ListDirectoryTool
├── RunCommandTool
├── WebRequestTool
└── SearchFilesTool
```

#### 组件职责

| 组件             | 职责                                               |
| ---------------- | -------------------------------------------------- |
| `Tool` (ABC)     | 工具抽象基类，定义接口规范，提供 `to_schema()` 方法 |
| `ToolRegistry`   | 工具注册中心，提供注册、查询、批量获取 schema       |
| `ToolExecutor`   | 工具执行引擎，支持单个/批量执行，返回 tool role 消息 |

#### 内置工具一览

```
┌─────────────────┬──────────────────────────────────────┐
│ 工具名           │ 功能说明                             │
├─────────────────┼──────────────────────────────────────┤
│ read_file       │ 读取指定路径的文件内容                │
│ write_file      │ 写入内容到指定路径                    │
│ list_directory  │ 列出目录下的文件和子目录               │
│ run_command     │ 执行 shell 命令（含危险命令黑名单）    │
│ web_request     │ 发送 HTTP 请求（基于 urllib）          │
│ search_files    │ 文件搜索（glob 模式 + 字符串匹配）    │
└─────────────────┴──────────────────────────────────────┘
```

**`run_command` 安全机制：** 内置命令黑名单（blocked commands），拦截危险操作如 `rm -rf /`、`format` 等，防止 LLM 生成破坏性指令。

#### 工具执行流程

```
LLM 返回 tool_calls
       │
       ▼
ToolExecutor.execute()
       │
       ├─► 从 tool_calls 解析 function name + arguments
       │
       ├─► ToolRegistry.get(name) 获取工具实例
       │
       ├─► tool.execute(**arguments) 执行工具
       │
       └─► 封装为 {"role": "tool", "content": result, ...}
           返回给 Agent 追加到消息列表
```

### 4.6 LLM 适配层

**目录：** `llm/`

LLM 层封装了与大语言模型的所有交互，通过统一接口适配不同的模型提供方。

#### 类关系

```
LLMClient (统一接口)
│
├── chat()         ── 普通对话（非流式）
├── stream_chat()  ── 流式对话
└── 内部持有 provider 实例
         │
         ├── OpenAIProvider
         │   ├── 基于 AsyncOpenAI 客户端
         │   ├── 支持 tool_calls 解析
         │   ├── 支持 normal + stream 两种模式
         │   └── 连接 OpenAI API 或兼容端点
         │
         └── LocalProvider (继承 OpenAIProvider)
             ├── 默认连接 localhost:11434/v1
             ├── 适配 Ollama 本地部署
             └── 复用父类全部逻辑，仅修改 base_url
```

#### Prompt 模板

`prompts.py` 定义了系统级提示词模板：

| 模板名                     | 用途                                        |
| -------------------------- | ------------------------------------------- |
| `SYSTEM_PROMPT`            | 主系统提示词，含 `{memory_context}`、`{plan_context}` 和 `{tool_descriptions}` 占位符 |
| `MEMORY_EXTRACTION_PROMPT` | 指导 LLM 从对话中提取值得记忆的信息         |

**System Prompt 注入流程：**

```
SYSTEM_PROMPT 模板
       │
       ├── {memory_context}      ◄── MemoryRetriever 返回的相关记忆
       │                              格式化为自然语言片段
       │
       ├── {plan_context}        ◄── TaskPlanner + _format_plan_context()
       │                              复杂任务时注入执行计划
       │
       └── {tool_descriptions}   ◄── ToolRegistry.schemas()
                                      所有工具的 JSON Schema 描述
```

### 4.7 Config 配置层

**目录：** `config/`

基于 Pydantic v2 构建的类型安全配置系统。

#### 配置结构

```
AppConfig
│
├── llm: LLMConfig
│   ├── provider       (openai / local)
│   ├── model          (模型名称)
│   ├── api_key        (API 密钥)
│   ├── base_url       (API 端点)

## 5. 核心数据流

### 5.1 单轮对话完整数据流

以下是用户发送一条消息到收到回复的完整流转过程：

```
 用户输入
    │
    ▼
 ┌─[1]─── CLI 接收输入 ───────────────────────────────────────┐
 │                                                              │
 │  InputHandler 处理输入 → Agent.run(user_input)               │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[2]─── 记忆检索 ────────────────────────────────────────────┐
 │                                                              │
 │  MemoryManager.retrieve(user_input)                          │
 │       │                                                      │
 │       ├─► MemoryRetriever → ChromaDB 向量搜索                │
 │       │                   → 关键词回退搜索                    │
 │       │                   → 混合评分排序                      │
 │       │                                                      │
 │       └─► 返回 top-k 相关记忆                                │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[3]─── 消息构建 ────────────────────────────────────────────┐
 │                                                              │
 │  Conversation.build_messages()                               │
 │       │                                                      │
 │       ├─► 将记忆注入 system prompt 的 {memory_context}       │
 │       ├─► 拼接历史对话（≤ 20 轮）                            │
 │       ├─► 追加当前用户输入                                    │
 │       └─► ContextManager 裁剪超出 token 限制的旧消息          │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[4]─── LLM 调用 ───────────────────────────────────────────┐
 │                                                              │
 │  LLMClient.chat(messages, tool_schemas)                      │
 │       │                                                      │
 │       └─► OpenAI/Local Provider → API 请求                   │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[5]─── ReAct 工具循环 ─────────────────────────────────────┐
 │                                                              │
 │  LLM 返回包含 tool_calls?                                    │
 │       │                                                      │
 │       ├─ 是 ─► ToolExecutor.execute(tool_calls)              │
 │       │        结果追加到 messages                            │
 │       │        回到步骤 [4] ← ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐          │
 │       │                                           │          │
 │       │        (循环直到无 tool_calls              │          │
 │       │         或达到 max_iterations) ─ ─ ─ ─ ─ ─┘          │
 │       │                                                      │
 │       └─ 否 ─► 提取 assistant 回复内容                       │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[6]─── 返回回复给用户 ─────────────────────────────────────┐
 │                                                              │
 │  Renderer 渲染 Markdown → 终端输出                           │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[7]─── 异步记忆处理 ───────────────────────────────────────┐
 │                                                              │
 │  MemoryManager.process_turn(user_input, assistant_reply)     │
 │       │                                                      │
 │       ├─► LLM 判断本轮对话是否包含值得记忆的信息              │
 │       │   (使用 MEMORY_EXTRACTION_PROMPT)                     │
 │       │                                                      │
 │       ├─► 若有 → 双写：                                      │
 │       │   ├── SQLite memories 表（结构化存储）                │
 │       │   └── ChromaDB（向量嵌入，供后续检索）                │
 │       │                                                      │
 │       └─► ShortTermMemory 更新（会话级缓存）                  │
 │                                                              │
 └──────────────────────────┬───────────────────────────────────┘
                            │
                            ▼
 ┌─[8]─── 对话历史更新 ───────────────────────────────────────┐
 │                                                              │
 │  Conversation.add_turn(user_input, assistant_reply)          │
 │       │                                                      │
 │       └─► 追加到历史列表，超过 20 轮时裁剪最旧记录            │
 │                                                              │
 └─────────────────────────────────────────────────────────────┘
```

### 5.2 记忆写入数据流

```
对话轮次完成
      │
      ▼
MemoryManager.process_turn()
      │
      ├─► 发送对话给 LLM + MEMORY_EXTRACTION_PROMPT
      │          │
      │          ▼
      │   LLM 返回提取的记忆条目
      │   (可能为空，若对话无需记忆)
      │
      ├─► 若提取到记忆：
      │   │
      │   ├─► SQLite: INSERT INTO memories
      │   │   (content, importance, timestamp, metadata)
      │   │
      │   ├─► ChromaDB: collection.add()
      │   │   (embedding vector + metadata)
      │   │
      │   └─► ShortTermMemory.add()
      │       (内存列表追加)
      │
      └─► 结束
```

### 5.3 记忆检索数据流

```
查询输入 (query)
      │
      ▼
MemoryRetriever.retrieve(query)
      │
      ├──► ChromaDB 向量搜索
      │    collection.query(query_embedding, n_results)
      │         │
      │         ▼
      │    candidates_vector = [{id, content, similarity, ...}]
      │
      ├──► 关键词回退 (若向量结果不足)
      │    遍历 SQLite memories 表做字符串匹配
      │         │
      │         ▼
      │    candidates_keyword = [{id, content, ...}]
      │
      ├──► 合并候选集，去重
      │
      ├──► 对每个候选计算混合得分：
      │    score = sim × 0.5 + importance × 0.3 + recency × 0.2
      │
      ├──► 按 score 降序排列
      │
      └──► 返回 top-k 结果
```

### 6.3 ChromaDB 向量存储

ChromaDB 为每条记忆存储向量嵌入，支持语义级别的相似度搜索：

```
ChromaDB Collection
├── document:  记忆文本内容
├── embedding: 文本向量表示 (由 LLM/嵌入模型生成)
├── metadata:  {importance, timestamp, source, ...}

**SQLite 与 ChromaDB 双写保持一致性**：每次记忆写入同时操作两个存储，SQLite 负责结构化查询和持久化，ChromaDB 负责语义检索。

## 8. 关键设计决策

### 8.1 ReAct + 自动规划 + 工具消息持久化

**决策**：采用 ReAct（Reasoning + Acting）模式 + 启发式自动规划 + 工具消息全量持久化。

**原因**：
- ReAct 让 LLM 能够交替进行推理和行动，通过工具获取真实信息后再推理，显著减少幻觉
- `max_iterations`（默认 30）防止无限循环，耗尽时返回明确中断提示并引导"继续"
- 工具调用消息（assistant tool_calls + tool results）实时持久化到 Conversation，确保"继续"时 LLM 保留完整上下文
- 零 LLM 开销的启发式复杂度评估自动触发规划，复杂任务有结构化计划指导，简单任务零开销直达

### 8.2 混合记忆检索策略

**决策**：向量语义搜索为主，关键词匹配为回退，结合三维混合评分。

**原因**：
- 纯向量搜索在短文本、专有名词上可能失准，关键词匹配作为补充可提高召回率
- 三维评分（相似度 + 重要性 + 时效性）比单一维度更贴合人类记忆的工作方式
- 72 小时半衰期的指数衰减模型使近期记忆自然获得更高权重，无需手动清理

### 8.3 SQLite + ChromaDB 双写

**决策**：记忆同时写入 SQLite 和 ChromaDB 两个存储引擎。

**原因**：
- SQLite 提供可靠的结构化存储、事务支持和关系查询能力（如按时间范围筛选、按重要性排序）
- ChromaDB 专注向量检索，提供高效的语义相似度搜索
- 双写虽有一致性风险，但在单机场景下可接受，换取的是查询灵活性的大幅提升

### 8.4 OpenAI 协议兼容设计

**决策**：`LocalProvider` 继承 `OpenAIProvider`，仅修改 `base_url`。

**原因**：
- Ollama、vLLM、LM Studio 等本地推理框架普遍兼容 OpenAI API 协议
- 通过继承复用全部调用逻辑，避免为每个本地框架编写适配代码
- 用户只需切换 `provider` 配置和 `base_url` 即可在云端与本地模型间无缝切换

### 8.5 配置加载四级优先级

**决策**：默认值 → YAML → 环境变量解析 → 环境变量覆盖。

**原因**：
- 代码内置默认值确保零配置也能启动
- YAML 文件适合版本控制和团队共享
- `${VAR}` 占位符解析支持在 YAML 中引用敏感信息（如 API Key），避免密钥硬编码
- 环境变量覆盖适合 CI/CD 和容器化部署场景

### 8.6 中英文混合 Token 估算

**决策**：`ContextManager` 对中文字符和英文单词采用不同的 token 估算比率。

**原因**：
- 大多数 tokenizer 中，一个中文字符通常消耗 1.5–2 个 token，而一个英文单词平均约 1.3 个 token
- 在不引入 tiktoken 等外部依赖的前提下，基于字符类型的启发式估算能提供足够准确的上下文窗口管理
- 避免因低估 token 数导致消息被截断，或因高估导致上下文利用率不足

### 8.7 工具安全 — 命令黑名单

**决策**：`run_command` 工具内置危险命令黑名单。

**原因**：
- LLM 可能被诱导执行破坏性命令（如 `rm -rf /`、`format C:`）
- 黑名单机制作为基本防线，在不严重限制功能的前提下拦截高危操作
- 配合 `ToolsConfig.ShellConfig` 可由用户自定义黑名单和超时时间

### 8.8 会话级短期记忆 + 持久化长期记忆

**决策**：短期记忆为内存列表（50 条上限），长期记忆持久化到 SQLite + ChromaDB。

**原因**：
- 模拟人类记忆的双系统模型：工作记忆（短期）容量有限但访问极快，长期记忆容量大但需要检索
- 短期记忆无需持久化，降低 I/O 开销
- 50 条上限防止内存膨胀，FIFO 淘汰保证保留最新信息
